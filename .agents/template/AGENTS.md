## Architecture

Shared patterns (barrel imports, theming, common widgets, dialogs, network, services, failures,
fixtures) are owned by the kit's `flutter-core-architecture` skill. Load that skill before creating
or extending anything shared, rather than working from a restated copy of its rules.

```
lib/
├── core/       components/ constants/ error/ models/ network/
│              repositories/ router/ services/ utils/
└── features/{feature}/  bloc/ model/ repo/ view/ widget/
```

## Hard rules

- All imports through the barrel; no cross-feature imports (share via `lib/core/`).
- No hardcoded colours, strings, assets or dimensions. Font sizes stay unscaled so OS text scaling
  works; layouts differ by breakpoint rather than by scaling. No `dynamic`. No
  `var` — declare explicit types, prefer `final`/`const`.
- No navigation, snackbars, dialogs or `BuildContext` in a bloc. Emit state; react in a listener.
- Break a complex `build` into private `StatelessWidget` classes rather than methods returning
  `Widget`.
- Reads return `Future<T?>`; writes return `Future<Either<Failure, T>>`.
- Never hard-code secrets. Sensitive values go in secure storage, never shared preferences. Never
  disable certificate validation. Validate any WebView URL against an allowlist.
- No `TODO` left behind. Comment *why*, not *what*.

## Skills

Type `/ask-kit` to find the right skill. The short version: `/grill` before building anything whose
criteria are thin, the two `*-e2e` skills to build, `flutter-code-review` and `flutter-verify` before
calling it done, `/release-readiness` before shipping.

Most skills are model-invoked and fire on their own. The heavy ones are commands and only start
when you type them.

## Verification

Never claim a feature works without naming the rung it was proven at. `flutter-verify` owns the
ladder and the baseline. A pre-existing failing test is recorded in `docs/agents/project.md`; check
it before reporting a failure as new.
